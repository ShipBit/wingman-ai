### 1.3 Desktop app support (Tauri / Electron / device flow / Bearer / Expo)

- **Official Electron integration (`@better-auth/electron`, since v1.5):** "The Electron plugin uses deep links to redirect users back to your app after authentication." Flow: system browser → hosted web sign-in page → custom protocol scheme (e.g. `com.example.app://`) → "The authorization code is a short-lived 32-character string" exchanged for a session; cookies/session stored locally via configurable `storage` (default `conf` package). Server: `plugins: [electron()]` and "add your app's protocol scheme to the trustedOrigins on your Better Auth server" e.g. `trustedOrigins: ["com.example.app:/"]`. Client options `signInURL`, `protocol`, `storage`. Security: "You should never expose the authClient directly to the renderer process". **No mention of Tauri.** (https://better-auth.com/docs/integrations/electron; announced in https://better-auth.com/blog/1-5)
- **Tauri: no official package.** Community plugin `@daveyplate/better-auth-tauri`: "Tauri plugin for Better Auth to handle OAuth & Magic Link etc"; server plugin with deep-link scheme, `tauri.conf.json` `plugins.deep-link.desktop.schemes`, client `setupBetterAuthTauri()` (plus React hook and "Svelte integration with lifecycle management"), `signInSocial()` helper using the Tauri Opener plugin; 83 stars; MIT; community-maintained (https://github.com/daveyplate/better-auth-tauri). Last commits: "0.1.9" and "Sanitize callback success redirect and escape HTML" on June 3, 2026 (https://github.com/daveyplate/better-auth-tauri/commits/main). npm: https://www.npmjs.com/package/@daveyplate/better-auth-tauri (not fetched; npm returned 403 for another package)
- **Device Authorization plugin (RFC 8628, introduced in v1.4, Nov 2025):** endpoints `POST /device/code`, `POST /device/token`, `GET /device`, `POST /device/approve`, `POST /device/deny`; "Device and user codes expire after the configured time (default: 30 minutes)"; polling "Default: '5s'"; designed for "smart TVs, CLI applications, IoT devices, and gaming consoles"; full CLI example with browser approval; `npx @better-auth/cli login` demo (https://better-auth.com/docs/plugins/device-authorization; https://better-auth.com/blog/1-4). v1.7 extended it: "Device authorization for OAuth clients — RFC 8628 grant enabling limited-input devices to request API access" (https://better-auth.com/blog/1-7)
- **OAuth 2.1 Provider plugin (Better Auth as authorization server — relevant if the Tauri app should be a standard public OAuth client):** "requires PKCE by default for all clients"; native apps may use "a claimed https URI", "an http loopback URI on exactly localhost, 127.0.0.1, or [::1] with any port", or "an authority-free private-use URI with a reverse-domain scheme such as com.example.app:/callback"; issues JWT access tokens (default 1 hour), refresh tokens (default 30 days), ID tokens (10 hours); RFC 7591 dynamic registration (https://better-auth.com/docs/plugins/oauth-provider)
- **Bearer plugin:** "enables authentication using Bearer tokens as an alternative to browser cookies"; get token from `set-auth-token` response header after sign-in, send as `Authorization: Bearer`; warning: "Use this cautiously; it is intended only for APIs that don't support cookies or require Bearer tokens for authentication. Improper implementation could easily lead to security vulnerabilities." No explicit desktop guidance (https://better-auth.com/docs/plugins/bearer)
- **Expo plugin (mobile reference pattern):** "Better Auth uses deep links to redirect users back to your app after authentication"; app scheme must be in `trustedOrigins`; session cached in `expo-secure-store`; "On native (iOS/Android), signIn.social does not navigate automatically" (https://better-auth.com/docs/integrations/expo)
- **Documented recommended approach for a desktop app (synthesis):** the official pattern is the Electron one — open system browser to your hosted sign-in page, return via custom scheme with a one-time 32-char code, exchange for a session stored locally. For Tauri you replicate this with the community plugin or your own deep-link handler. Alternatives with official docs: Device Authorization flow (code + browser approval, good for "no deep link" cases), or OAuth 2.1 Provider with loopback/custom-scheme PKCE public client yielding JWTs.

### 1.4 Session lifetime, cookie cache, JWT plugin

- "The session expires after 7 days by default" (`expiresIn: 60 * 60 * 24 * 7`); `updateAge` default 1 day ("every 1 day the session expiration is updated"); "By default, the freshAge is set to 1 day"; `cookieCache` default `maxAge: 5 * 60`; `disableSessionRefresh: true` stops rolling refresh; customSession plugin for custom session response (https://www.better-auth.com/docs/concepts/session-management)
- Options reference: `session.expiresIn` default "604800", `session.updateAge` default "86400", `cookieCache.enabled` default "false", `strategy: "jwt"` example; **"Maximum session duration: Not explicitly stated"** — values are plain seconds, so 90+ day sessions are just `expiresIn: 60*60*24*90` (no documented cap) (https://better-auth.com/docs/reference/options)
- v1.6 breaking change: "The freshAge check now uses createdAt instead of updatedAt" (prevents indefinitely fresh sessions) (https://better-auth.com/blog/1-6)
- **JWT plugin:** "provides endpoints to retrieve a JWT token and a JWKS endpoint to verify the token" for "services that can't use the session"; JWKS at `/api/auth/jwks` by default, customizable via `jwksPath` to "/.well-known/jwks.json"; get token via `authClient.token()`, the `/token` endpoint, or the `set-auth-jwt` header on `getSession`; "The expiration time is set to 15 minutes" (configurable); algorithms EdDSA (Ed25519/Ed448), ES256, ES512, RSA256, PS256, ECDH-ES; `definePayload` to shape claims; verification example uses `jose` — **no Python example, but JWKS is a standard so PyJWT/authlib can verify** (my inference) (https://www.better-auth.com/docs/plugins/jwt). v1.4 added "JWT Key Rotation: Rotate keys without downtime" (https://better-auth.com/blog/1-4)

### 1.6 Bulk import / migration, users without password, account linking

- Official migration guides exist for Supabase, Clerk, Auth0, Auth.js, WorkOS (https://better-auth.com/docs/guides/supabase-migration-guide, https://better-auth.com/docs/guides/clerk-migration-guide, https://better-auth.com/docs/guides/auth0-migration-guide, https://better-auth.com/docs/guides/next-auth-migration-guide, https://better-auth.com/docs/guides/workos-migration-guide)
- Import mechanism = **direct DB insert via the adapter**, not the public API: `ctx.adapter.create({ model: "user", data: {...}, forceAllowId: true })` (keeps original IDs); password hashes go in an `account` row with `providerId: "credential"` and `password: <hash>`; bcrypt kept by configuring `password: { hash, verify }`; OAuth-only users get `account` rows with `providerId`/`accountId` and **no password** ("enabling login via social authentication alone") (https://better-auth.com/docs/guides/auth0-migration-guide; https://better-auth.com/docs/guides/clerk-migration-guide)
- **Admin plugin `createUser` requires a password** ("password: string … required"); supports `role` and `data` ("Extra fields for the user. Including custom additional fields"); "The plugin does not document a method for creating users without passwords" (https://better-auth.com/docs/plugins/admin)
- **Users without password can log in via magic link / email OTP** because both auto-create/accept accounts by email (see 1.2 defaults) — so inserting `user` rows without any `account` row and letting them use magic link / OTP / password reset is consistent with the docs (inference from https://better-auth.com/docs/plugins/magic-link and https://better-auth.com/docs/plugins/email-otp).
- **Account linking:** "Account linking is enabled by default" and automatically connects OAuth providers "when their email verification status is confirmed or the provider is trusted"; `trustedProviders` bypasses email-verification check ("Use this with caution as it may increase the risk of account takeover"); `allowDifferentEmails: true` links accounts with different/no email; `updateUserInfoOnLink`; `disableImplicitLinking: true`; manual `linkSocial()` / `unlinkAccount()` (https://better-auth.com/docs/concepts/users-accounts). Options: `accountLinking.enabled` default "true", `allowDifferentEmails` default "false" (https://better-auth.com/docs/reference/options)

### 1.7 Backend verification and user events

- Python backend verifies JWTs against the JWKS endpoint (1.4). Session-based check alternative: call `/api/auth/get-session` on the TS server (not fetched as a separate page; inferred from the JWT plugin's "services that can't use the session" wording, https://www.better-auth.com/docs/plugins/jwt)
- **No external webhooks feature** found in docs. Instead: `databaseHooks` for `user`, `session`, `account`, `verification` with `before`/`after` (https://better-auth.com/docs/reference/options); before hooks can abort/replace data, after hooks for follow-up actions (https://better-auth.com/docs/concepts/database); endpoint before/after hooks with example "sendMessage({ type: 'user-register', … })" on `/sign-up`, and `runInBackground` for fire-and-forget (https://better-auth.com/docs/concepts/hooks). v1.5: "Database 'after' hooks now execute after the transaction commits, not during it" (https://better-auth.com/blog/1-5)

### 1.8 EU data residency

- Self-hosted; data lives wherever you deploy the server + DB (e.g. Vercel Frankfurt region + EU Postgres). No provider-side residency concept. (Derived from hosting model in https://better-auth.com/docs/installation.) Only the optional Infra dashboard would send audit logs/detections to Better Auth's cloud (https://better-auth.com/pricing).

- **Security advisories (heavy in 2026):** "Security update: June 2026" (Jun 2, 2026) covered **14 advisories** — core: "OAuth account linking ownership (High) – fixed in 1.6.11"; device auth: "Device-flow owner binding (High, CVE-2026-45337)"; OAuth provider ×4; SCIM; SSO "Registration URL validation (Critical)"; OIDC/MCP "Refresh-token handling (Critical)", "Protocol defaults (High)"; a "dedicated security-review workstream" was started (https://better-auth.com/blog/security-update-june-2026). GitHub advisories pages list e.g. GHSA-8c5h-wx78-2cfg (High, Aug 11, 2026, SSO), GHSA-qq9h-g4jm-xgf3 "pre-account hijacking on magic-link and email-OTP sign-in" (High, Jun 26, 2026), GHSA-g38m-r43w-p2q7 "pre-account hijacking via OAuth implicit linking (nOAuth-class)" (High, May 31, 2026), GHSA-p6v2-xcpg-h6xw rate limiter IPv6 bypass (High, May 11, 2026), GHSA-9h47-pqcx-hjr4 "alg=none advertised and plain PKCE accepted by default" in oidcProvider (High) (https://github.com/better-auth/better-auth/security/advisories; https://github.com/better-auth/better-auth/security/advisories?page=2). Third-party CVE write-ups: CVE-2026-67336 (CVSS 8.7, fixed 1.6.11) (https://www.sentinelone.com/vulnerability-database/cve-2026-67336/), CVE-2025-61928 unauthenticated API-key creation, fixed 1.3.26 (https://advisories.gitlab.com/pkg/npm/better-auth/CVE-2025-61928), CVE-2025-53535 open redirect, fixed 1.2.10 (https://advisories.gitlab.com/pkg/npm/better-auth/CVE-2025-53535)
- **Honest assessment for a 2-person team:** Better Auth is *not* "clearly simpler" than a hosted provider. You get zero per-MAU cost, full data ownership, trivial EU hosting, Vercel backing and a very active project, plus the official Electron pattern and RFC 8628 device flow that map well to a desktop app. Against that: you run and patch a TS server + DB, you own email delivery, you follow a release train that ships patches weekly and has broken things on minor versions repeatedly (1.3→1.7, then a 1.7.3 rollback), and 2025–2026 brought a long list of High/Critical advisories, several in core flows you would actually use (implicit account linking, magic link / email OTP pre-account hijack). Most of the remaining advisories are in optional plugins (oauth-provider, sso, scim, oidc, mcp) you could simply not enable. Net: cheaper and more flexible, but expect ongoing maintenance effort and to pin/upgrade deliberately.

### Key takeaways — Better Auth for Tauri desktop + website
- Website (SvelteKit on Vercel) hosts Better Auth; the Tauri app opens the system browser to that site and returns via custom scheme with a one-time code (official Electron pattern; community Tauri plugin exists). Or use the Device Authorization plugin for a deep-link-free "enter code in browser" flow.
- Sessions can be 90+ days (`expiresIn` in seconds, no documented max); pair with the JWT plugin (15-min JWTs by default, JWKS at `/api/auth/jwks`) so the Python backend verifies statelessly.
- Google/Discord/GitHub/Apple/Microsoft/X/Twitch are built in; Steam only via small community OpenID 2.0 plugins (0-star repos) or your own plugin.
- Migration = direct DB inserts (official guides); passwordless users can use magic link / email OTP; automatic linking by verified email is on by default.
- Budget time for upgrades and security patches.

## 4. ORY NETWORK (brief)

1. **Pricing:** "Developer — Free — 2 development environments, 0 production"; "Production — $770 / year — included monthly credit $21.00 — $0.14 / aDAU / month — $0.007 / M2M token — 1 production environment and 3 staging environments — GDPR-compliant EU data storage — custom domains (1)"; "Growth — $9,350 / year — $255.00 credit — $0.12 / aDAU / month — 2 production + 5 staging, B2B organizations (max 3)"; Enterprise custom ("99.99% uptime SLA", multi-region). A monthly/yearly toggle exists; monthly prices were not captured (https://www.ory.com/pricing)
2. **Unit definition (DAU not MAU):** "Average Daily Active Users (aDAUs) measures the average number of unique users who use the Ory Identities APIs on a daily basis" (https://www.ory.com/pricing)
3. **Social providers:** "custom-tailored connectors for 15+ social sign-in providers such as GitHub, Google, or Facebook" plus "any OpenID Connect-compliant identity provider using the Generic provider integration" (https://www.ory.com/docs/kratos/social-signin/overview). Confirmed pages: Discord ("Add Discord as a social sign-in provider in Ory") (https://www.ory.com/docs/kratos/social-signin/discord), Twitch (https://www.ory.com/docs/kratos/social-signin/twitch), X/Twitter (https://www.ory.com/docs/kratos/social-signin/x-twitter); index also lists Apple, Microsoft, GitHub, Google, Facebook, Amazon, Slack, LinkedIn, GitLab, Spotify (https://www.ory.com/docs/llms.txt). **Steam:** the docs index lists "Sign in with Steam" at https://www.ory.com/docs/integrates-with/social-signin/steam, but that URL (and /kratos/social-signin/steam) returned 404 → could not verify.
4. **Passwordless/password:** "one-time code sent via email and SMS" (https://www.ory.com/docs/network/kratos/passwordless/one-time-code); username/email + password supported (https://www.ory.com/docs/kratos/concepts/credentials/username-email-password); magic link page → could not fetch (404) / NOT FOUND.
5. **Desktop/native:** "Native applications such as desktop applications, mobile applications, or terminal-based apps that do not run inside a browser should use session tokens instead of session cookies" (https://www.ory.com/docs/kratos/session-management/overview); native apps use `/self-service/{flow-type}/api` and "receive an Ory Session Token instead of an Ory Session Cookie" (https://www.ory.com/docs/identities/native-browser). Social sign-in for native apps: browser window (ASWebAuthenticationSession / Custom Tabs), return via "iOS Universal Link or Android App Link", then exchange "session token exchange code for a session token" — **iOS/Android only; no desktop/custom-scheme/loopback docs** (https://www.ory.com/docs/kratos/social-signin/native-apps)
6. **Session lifetime:** configured as duration strings; "to set the session lifespan to 30 days, enter 720h"; **default NOT FOUND on page; no max stated** (https://www.ory.com/docs/kratos/session-management/session-lifespan); refresh by calling login with `refresh: true` (https://www.ory.com/docs/kratos/session-management/overview)
7. **Custom metadata / JWT claims:** `traits` (user-editable), `metadata_public` ("visible to anyone having access to the user's sessions"), `metadata_admin` (admin API only) (https://www.ory.com/docs/kratos/manage-identities/managing-users-identities-metadata). Session-to-JWT via `/sessions/whoami?tokenize_as=…`, claims built with Jsonnet from `session` data, TTL "defaults to 10 minutes", you supply the JWKS ("base64://" literal), "Ory recommends to use ES256 or ES512"; backends verify with the public key (https://www.ory.com/docs/identities/session-to-jwt-cors)
8. **Bulk import:** `PATCH /admin/identities` with "a JSON array of identities, each of which must have a create property"; hashes "BCrypt, Argon2, MD5, SHA, SSHA…, PBKDF2, SCrypt, Firebase SCrypt, crypt(3), HMAC"; passwordless import via "an empty password hash and use_password_migration_hook set to true"; social identities via `provider` + `subject`; **force reset NOT FOUND** (https://www.ory.com/docs/kratos/manage-identities/import-user-accounts-identities)
9. **Auto-linking:** only Google and Apple — "users who sign in with Google or Apple are automatically linked to an existing account if both identities share the same verified email address"; other providers require "an additional verification step, like password or passkey input" (https://www.ory.com/docs/kratos/social-signin/link-multiple-provider-account). **Webhooks (Actions):** before/after registration, login, settings; non-blocking (`response.ignore: true`) or blocking (`response.parse: true` can "modify the identity, interrupt the flow") (https://www.ory.com/docs/guides/integrate-with-ory-cloud-through-webhooks)
10. **EU residency:** "When you create a new Ory Network project in the Ory Console, you are given a choice of personal data storage location" (EU / US; "Global" and "US Continental" for enterprise); "this choice is permanent for that project" (https://www.ory.com/docs/security-compliance/personal-data-location); "hosting personal data exclusively on EU based servers"; ISO 27001:2022 and SOC 2 Type 2 (https://www.ory.com/docs/security-compliance/compliance-and-certifications)

**Takeaways (Tauri + website):** Broadest provider coverage of the hosted three (Discord/Twitch/X confirmed, Steam listed but unverifiable), first-class "native app = session token" model with long configurable sessions, EU project region, JWT-from-session with your own keys for the Python backend. Costs: no free production tier — Production is "$770 / year" plus $0.14/aDAU beyond a $21/month credit; desktop social sign-in return path (custom scheme/loopback) is not documented, you'd implement it around the API flow yourself.
