### 3. Desktop app support (Tauri)

- Application types: "Native Applications: mobile or desktop applications that run natively on a device (such as iOS or Android)"; SPA: "JavaScript apps that perform most of their user interface logic in a web browser" (https://auth0.com/docs/get-started/applications).
- Loopback/custom scheme: "Applications running on a local machine (e.g., desktop apps, CLIs) use the loopback interface for callbacks (e.g., http://127.0.0.1:51089/callback or http://localhost:61024/callback)"; "Custom URI schemes pose a risk as more than one application on the device can register the same scheme"; both are "Non-Verifiable Callback URIs"; Auth0 "displays a confirmation prompt when non-verifiable callback URIs are detected", adjustable at application and tenant level under Advanced settings (https://auth0.com/docs/secure/security-guidance/measures-against-app-impersonation).
- Official Electron sample: `auth0-samples/auth0-electron-samples` redirects to `okta-graveyard`; README: "This example is DEPRECATED and is not working properly. We are working on a new version of it."; archived April 2, 2019 (https://github.com/auth0-samples/auth0-electron-samples). There is no maintained official Electron or Tauri quickstart in the fetched material.
- Auth0's own .NET desktop library (`Auth0.OidcClient.WPF/WinForms/UWP`) exists, built on IdentityModel.OidcClient (https://github.com/auth0/auth0-oidc-client-net); its callback doc lists `https://YOUR_AUTH0_DOMAIN/mobile` for WPF/WinForms and no loopback format (https://auth0.github.io/auth0-oidc-client-net/documentation/getting-started/callbacks.html).
- Community Tauri examples (third-party):
  - dev.to, June 2, 2025 (SvelteKit + Tauri): uses `@auth0/auth0-spa-js` with an Auth0 **SPA** app type, `tauri-plugin-deep-link` + `opener` plugin (system browser), redirect `agx://localhost/auth` on desktop / `http://localhost:1420` in dev; `cacheLocation: "localstorage"`, `useRefreshTokens: true`; gotcha: "Must explicitly add `tauri://localhost` and `https://tauri.localhost` as Web Origins in Auth0 settings" because the Tauri webview sets those origins; deep links only work in `tauri build`, not dev (https://dev.to/yannamsellem/adding-auth0-to-your-tauri-app-secure-authentication-for-agx-on-web-and-desktop-1h4k).
  - dev.to, May 6, 2023: system browser + custom protocol `myapp:auth?code=…` via `tauri-plugin-deep-link`, tokens in the `keyring` crate; notes Tauri's `on_navigation` cannot intercept external navigations, so you shouldn't load Auth0 inside the webview (https://dev.to/randomengy/using-auth0-with-tauri-14nl).
  - Tauri discussion #3020 (Dec 2021 →): Apple WebKit "prevents redirects to non-HTTPS protocols, blocking tauri://localhost redirects"; community consensus points to `tauri-plugin-oauth` ("system browser + localhost loopback server"); "No official Tauri maintainer recommendation is documented" (https://github.com/tauri-apps/tauri/discussions/3020).
- Refresh tokens for native/SPA: Auth0 "limits the amount of active refresh tokens to 200 tokens per user per application"; rotation "issues a new refresh token and invalidates the predecessor token with each request" and is recommended for SPAs against ITP (https://auth0.com/docs/secure/tokens/refresh-tokens; https://auth0.com/docs/secure/tokens/refresh-tokens/refresh-token-rotation).

### 4. Session / refresh-token lifetimes (exact numbers)

- Refresh token **Idle lifetime default: "2,592,000 seconds (30 days)"**; idle and maximum lifetime both cap at **"31,557,600 seconds (1 year)"** ("365.25 days to account for leap years"); "The Idle Refresh Token Lifetime can not exceed the Maximum Refresh Token Lifetime"; if the maximum-lifetime toggle is disabled "the maximum lifetime will be indefinite"; configured per application under Applications > Settings > Refresh Token Expiration or via `PATCH /api/v2/clients/{id}` (`token_lifetime`, `idle_token_lifetime`, `infinite_token_lifetime`, `infinite_idle_token_lifetime`). No plan restriction is mentioned on this page (https://auth0.com/docs/secure/tokens/refresh-tokens/configure-refresh-token-expiration). A default for the *maximum* lifetime is not stated on the page (NOT FOUND).
- Rotation/reuse detection: on reuse Auth0 "invalidates … all refresh tokens … from the original refresh token issued for the client"; default reuse interval NOT FOUND on the page (https://auth0.com/docs/secure/tokens/refresh-tokens/refresh-token-rotation).
- **Login session (Universal Login cookie) limits** — table "Maximum (Self-Service plans)" vs "Maximum (Enterprise Plans)": Idle timeout (Inactivity) **3 days** self-service / **100 days** enterprise; Absolute timeout (Require login after) **30 days** self-service / **365 days** enterprise (https://auth0.com/docs/manage-users/sessions/session-lifetime-limits). Dashboard settings are in minutes: "Idle Session Lifetime (Persistent/Non-Persistent)", "Maximum Session Lifetime (Persistent/Non-Persistent)"; Management API uses hours (`session_lifetime`, `idle_session_lifetime`, `ephemeral_session_lifetime`, `idle_ephemeral_session_lifetime`) (https://auth0.com/docs/manage-users/sessions/configure-session-lifetime-settings).
- Defaults "Inactivity timeout 4320 minutes (3 days)" and "Require log in after 10080 minutes (7 days)" appeared only in search-result summaries of Auth0 community/docs pages (e.g. https://community.auth0.com/t/login-session-management-inactivity-timeout-and-require-log-in-after/106379); the fetched docs pages did not state defaults → treat as unconfirmed.
- "Long Lived Sessions" is an Enterprise-only line item on the pricing page (https://auth0.com/pricing). For a desktop app the relevant lever is the refresh-token lifetime (up to 1 year, any plan per the docs), not the browser session.

### 5. User metadata and custom claims

- `user_metadata`: "user attributes such as preferences that do not impact a user's core functionality", "can be edited by logged in users"; `app_metadata`: "permissions, Auth0 plan, and external IDs that can impact user access to features", "cannot be edited by users" (https://auth0.com/docs/manage-users/user-accounts/metadata).
- Limits: "Auth0 user profiles have a size limit of 10 KB"; "a 1 MB per-user limit on user data" for indexed/searchable data; signup endpoint "maximum of 10 string fields whose values do not exceed 500 characters each"; "Field names must not contain the `.` (dot) or `$` (dollar sign) characters"; restricted `app_metadata` keys: `__tenant, _id, blocked, clientID, created_at, email_verified, email, globalClientID, global_client_id, identities, lastIP, lastLogin, loginsCount, metadata, multifactor_last_modified, multifactor, updated_at, user_id` (https://auth0.com/docs/manage-users/user-accounts/metadata/metadata-fields-data).
- Management API: `GET /api/v2/users/{id}`, `PATCH /api/v2/users/{id}` (https://auth0.com/docs/manage-users/user-accounts/metadata).
- Custom claims via post-login Action: `api.idToken.setCustomClaim('claim_name', value)` / `api.accessToken.setCustomClaim(...)`; "Auth0 allows namespaced and non-namespaced claims, but certain restrictions apply" — namespacing recommended, not required; reserved: "auth0.com, webtask.io, webtask.run" and "urn:auth0"; standard OIDC claims and 60+ names (`sub`, `aud`, `iss`, `roles`, `permissions`, `groups`, `org_id` …) cannot be set; "Custom claims payload is set to a maximum of 100KB" (https://auth0.com/docs/secure/tokens/json-web-tokens/create-custom-claims).

### 6. Bulk import, passwords, account linking, lazy migration

- Bulk import needs "a database connection using the Auth0 user store" or a custom DB "with import mode on"; "The file size limit for a bulk import is 500KB" (~1,000 users with <10 metadata fields); "Users with passwords hashed by unsupported algorithms must reset their password when they log in for the first time after the bulk import" (https://auth0.com/docs/manage-users/user-migration/bulk-user-imports).
- Schema: `email` required; `email_verified` (default false), `user_id` ("will be prepended by the connection strategy", i.e. becomes `auth0|<your id>`), `password_hash` (bcrypt "$2a$" or "$2b$", "10 saltRounds"), `custom_password_hash` (argon2, bcrypt, hmac, ldap, md4, md5, sha1, sha256, sha512, pbkdf2, scrypt), `app_metadata`, `user_metadata`, `username`, `blocked`, `mfa_factors` all optional; the basic example imports a user with only `email`, `email_verified`, `app_metadata` (no password) (https://auth0.com/docs/manage-users/user-migration/bulk-user-import-database-schema-and-examples).
- Setting a password afterwards: `POST /dbconnections/change_password` sends the reset email; Management API "Create a Password Change Ticket … generates a URL like the one in the password reset email" — "If you use the ticket URL, your application is responsible for verifying the identity of the user in some other way" (https://auth0.com/docs/authenticate/database-connections/password-change). Whether tickets work for never-set passwords is not stated there (NOT FOUND). Auth0 Support (Sept 10, 2025) describes users "who have not set a password yet" after import as those "missing both the logins_count and last_password_reset" in an export — i.e. import-without-password + reset is a supported pattern (https://support.auth0.com/center/s/article/Identifying-Users-Without-Auth0-Password-After-Migration). An older community answer (July 22, 2022) claimed "a password is mandatory" and suggested random passwords + reset emails — superseded by the schema doc above (https://community.auth0.com/t/bulk-import-w-o-password-reset-password-for-users-without-passwords/86912).
- Account linking: docs describe user-initiated linking and "suggested" linking ("find accounts with the same email, and prompt the users to link them"); "your tenant should request authentication for both accounts before linking occurs"; sub-pages: link-user-accounts (Management API), suggested-account-linking-server-side-implementation, user-initiated-account-linking-client-side-implementation, account-link-extension; "Both your specific login implementation and your Auth0 plan or custom agreement affect whether this feature is available" (https://auth0.com/docs/manage-users/user-accounts/user-account-linking). Pricing page: Account Linking is Essentials and above, not Free (https://auth0.com/pricing). The Account Link Extension page has no deprecation notice but "depends on Rules" (https://auth0.com/docs/customize/extensions/account-link-extension); search snippets from Auth0 Community/Macnica say Rules/Hooks reached EOL 2024-11-18 and "Actions, in their current state, do not support account linking", leaving the Management API as the path (https://community.auth0.com/t/migrating-account-link-extension-to-actions/112415, https://community.auth0.com/t/account-linking-extension-action-problem/194124 — snippets only). Fully automatic link-by-verified-email: NOT FOUND as a supported first-party feature.
- Automatic (lazy) migration: custom DB connection with Login + Get User scripts; "Auth0 authenticates against your external user store and, if successful, creates the user in the Auth0 user store using the same ID and password"; keep "Import Users to Auth0" on (https://auth0.com/docs/manage-users/user-migration/configure-automatic-migration-from-your-database). Custom Database Connections are "Not available" on Free/Essentials, "Included" on Professional/Enterprise (https://auth0.com/pricing). Note: this needs a database that Auth0 can call — B2C won't expose password hashes, so this path doesn't apply to a B2C source.

### b. Does External ID fix the "re-login every 24 hours" problem?

Why it happens today (B2C): "Single-page applications using the authorization code flow with PKCE always have a refresh token lifetime of 24 hours while mobile apps, desktop apps, and web apps do not experience this limitation." B2C refresh token lifetime: default 14 days, min 1 day, max 90 days; sliding window `rolling_refresh_token_lifetime_secs` default 90 days, max 365 days, or `allow_infinite_rolling_refresh_token`; access/ID tokens 5–1,440 minutes (ms.date 2025-02-17, https://learn.microsoft.com/en-us/azure/active-directory-b2c/configure-tokens). B2C web session: "You can set the session lifetime up to 24 hours" (900–86,400 s), Rolling/Absolute; KMSI "1 to 90" days (https://learn.microsoft.com/en-us/azure/active-directory-b2c/session-behavior). So MSAL-browser in the Tauri webview registered as a SPA gets a 24-hour refresh token — this is the limit you are hitting, and it exists identically in External ID.

External ID / Microsoft identity platform (ms.date 2025-11-05): refresh-token default lifetime "24 hours for single-page applications", "24 hours for apps that use email one-time passcode authentication flow", "90 days for all other scenarios"; "Refresh tokens sent to a redirect URI registered as `spa` expire after 24 hours … apps must be prepared to rerun the authorization code flow using an interactive authentication to get a new refresh token every 24 hours" (https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens).
- Not configurable: "As of January 30, 2021, refresh and session token lifetimes are no longer configurable through token lifetime policies"; defaults "Refresh Token Max Inactive Time 90 days", max age "Until-revoked"; "To control how frequently users are required to sign in, use Conditional Access sign-in frequency instead"; access/ID token lifetime policies 10 min–1 day (ms.date 2026-04-08, https://learn.microsoft.com/en-us/entra/identity-platform/configurable-token-lifetimes).
- Microsoft staff answer (Q&A, 2026-04-14): Email OTP → "That 24-hour window is a hard cutoff for OTP flows"; local email+password or social IdPs → "By default that bucket gets a 90-day refresh-token lifetime, provided you're requesting offline_access and following the auth code + PKCE pattern" (https://learn.microsoft.com/en-us/answers/questions/5859191/clarification-on-refresh-token-lifetime-for-extern). A separate Q&A about 24-hour logouts in a CIAM SPA (2025-10-21) is unanswered (https://learn.microsoft.com/en-au/answers/questions/5592108/how-to-extend-session-lifetime-beyond-24-hours-in).
- Third-party (dev.to, May 20, 2024): External ID showed `AADSTS700082 … inactive for 12:00:00` — attributed to a default Conditional Access sign-in-frequency in External ID; fix was a CA policy "Sign-in frequency → Periodic reauthentication, 90 days" (https://dev.to/samvanhoutte/fixing-aadsts700082-refresh-tokens-expiring-after-12-hours-in-azure-entra-external-id-1mj0). External tenants support the CA session controls "Sign-in frequency" and "Persistent browser session"; "Stay signed in?" prompt shown by default (https://learn.microsoft.com/en-us/entra/external-id/customers/concept-supported-features-customers).
- Desktop path that gets the 90-day bucket: the official External-ID Electron quickstart registers the redirect URI under the "Mobile and desktop applications" platform with `http://localhost`, uses MSAL Node, and states "MSAL-browser is not supported in Electron applications"; MAUI uses `msal{client_id}://auth` (https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-desktop-app-sign-in?pivots=external&tabs=node-js-external). External tenants offer platforms "Public client (mobile and desktop) / Web / SPA" (https://learn.microsoft.com/en-us/entra/external-id/customers/concept-supported-features-customers).

Answer: External ID does **not** change the SPA rule. The fix (on B2C today or External ID later) is to stop being a SPA: register the desktop app as a public client (mobile & desktop platform), do auth-code+PKCE from the app (not msal-browser), use a loopback/custom-scheme redirect, request `offline_access`, avoid email OTP as the primary factor, and check the CA sign-in-frequency default.

### c. Identity providers, OTP, passkeys

External tenant primary sign-in methods: Email with password, Email one-time passcode, Passkey (FIDO2), Apple federation, Facebook federation, Google federation, Microsoft personal account (via OpenID Connect), Microsoft Entra ID federation, OpenID Connect federation, SAML/WS-Fed federation; SMS is MFA-only (https://learn.microsoft.com/en-us/entra/external-id/customers/concept-supported-features-customers; FAQ lists "Facebook, Google, Apple, Microsoft Entra ID federation, custom OIDC, and SAML/WS-Fed", https://learn.microsoft.com/en-us/entra/external-id/customers/faq-customers).
- GitHub, Discord, Twitch, X, Steam: not listed. Custom OIDC federation (ms.date 2026-07-29) requires a "Well-known endpoint" (OIDC discovery with `issuer`, `authorization_endpoint`, `token_endpoint`, `jwks_uri` …), `client_secret_post`/`client_secret_jwt`, and "only the `code` response type is supported"; no generic OAuth2 (non-OIDC) connector is documented (https://learn.microsoft.com/en-us/entra/external-id/customers/how-to-custom-oidc-federation-customers). B2C had GitHub (preview), Amazon, LinkedIn, QQ, WeChat, Weibo, X built-in (https://learn.microsoft.com/en-us/azure/active-directory-b2c/faq); migration doc: "Third-party identity providers configured through B2C custom policies aren't supported" in External ID (https://learn.microsoft.com/en-us/entra/external-id/customers/migrate-from-b2c-to-external-id). Steam (OpenID 2.0) therefore has no path here.

### d. B2C → External ID migration and B2C retirement

- "Effective May 1, 2025 Azure AD B2C will no longer be available to purchase for new customers … new tenants can only be created with Azure AD B2C P1. Azure AD B2C P2 will be discontinued on March 15, 2026, for all customers … We'll continue supporting Azure AD B2C until at least May 2030"; P2 tenants "automatically switched to P1 … by the end of March 2026" (B2C FAQ, ms.date 2025-06-20, https://learn.microsoft.com/en-us/azure/active-directory-b2c/faq). External ID FAQ: "We'll provide a migration path for existing custom policies in B2C when it becomes available" (https://learn.microsoft.com/en-us/entra/external-id/customers/faq-customers).
- Official guidance (ms.date 2026-03-13): "Standard migration" (most tenants) vs "High Scale Compatibility (HSC) mode" (≈5M+ directory objects; HSC has "no social identity providers, no passkeys …"); patterns: bulk user migration via Microsoft Graph then cutover, bulk + JIT password migration, or B2C-initiated credential harvesting (https://learn.microsoft.com/en-us/entra/external-id/customers/plan-your-migration-from-b2c-to-external-id, https://learn.microsoft.com/en-us/entra/external-id/customers/migrate-from-b2c-to-external-id).
- Password hashes: not exportable; the doc's no-preservation options include social IdPs, passwordless, or "requiring users to reset their password"; JIT uses the `OnPasswordSubmit` custom authentication extension to validate against the legacy IdP and write the password (https://learn.microsoft.com/en-us/entra/external-id/customers/migrate-from-b2c-to-external-id). Official tool `microsoft/b2c-to-meeid-migration-tool` is marked "PREVIEW/SAMPLE", MIT: bulk export/import plus "seamless password migration on first login (JIT)" — users get random passwords + a `RequireMigration` flag, an Azure Function validates via ROPC against B2C; also migrates MFA phone, app registrations, API connectors → custom extensions (https://github.com/microsoft/b2c-to-meeid-migration-tool/).
- Feature mapping: custom policies → custom authentication extensions; token customization → extensions/Attributes & Claims; age gating not supported (https://learn.microsoft.com/en-us/entra/external-id/customers/migrate-from-b2c-to-external-id).

### e. Custom attributes, claims, Graph, data residency

- Custom user attributes are directory extension attributes on `b2c-extensions-app`, types String/Boolean/Int, addressed as `extension_{appId-without-hyphens}_{name}`, manageable via Graph (https://learn.microsoft.com/en-us/entra/external-id/customers/how-to-define-custom-attributes). Add to tokens via Enterprise application > Single sign-on > Attributes & Claims > "Directory schema extension", then set `acceptMappedClaims: true` and `isFallbackPublicClient: true` in the manifest (ms.date 2025-09-16, https://learn.microsoft.com/en-us/entra/external-id/customers/how-to-add-attributes-to-token). Custom claims providers via `TokenIssuanceStart` extension; "All features that are supported in external tenants are also supported for automation through Microsoft Graph APIs" (https://learn.microsoft.com/en-us/entra/external-id/customers/concept-supported-features-customers).
- Data residency: "Country/Region … can't be changed later" at tenant creation (https://learn.microsoft.com/en-us/entra/external-id/customers/how-to-create-external-tenant-portal); geo-locations include "Europe, Middle East, and Africa (EMEA)"; Go-Local (paid) only Australia and Japan; US Gov/China not available for external tenants (ms.date 2025-11-06, https://learn.microsoft.com/en-us/entra/fundamentals/data-residency).
- Log retention in external tenants: "Seven days"; User Insights retiring Aug 31, 2026 (https://learn.microsoft.com/en-us/entra/external-id/customers/concept-supported-features-customers).

## Key takeaways for a Tauri desktop app + website

**Auth0**
- Cost: $0 up to 25,000 MAU on Free, including custom domain, unlimited social, Actions for custom claims, passwordless, and (per docs) 1-year refresh tokens. At >25k the jump is to Essentials $1,400 (20k) / $2,100 (30k). Account Linking, Role Management, Log Streams need Essentials ($70 @ 1k … $700 @ 10k). Custom DB/lazy migration needs Professional.
- 24-hour problem: solved by design — refresh-token idle default 30 days, max 1 year, per-app setting; rotation + reuse detection available. Register the Tauri app as **Native** and use system browser + loopback (`http://127.0.0.1:port`) or a custom scheme; expect Auth0's "non-verifiable callback" confirmation prompt (can be disabled). If you keep `auth0-spa-js` in the webview, add `tauri://localhost` and `https://tauri.localhost` as Web Origins — but no official Tauri/Electron sample exists (the Electron one is dead since 2019).
- IdPs: Google, GitHub, Apple, Microsoft, X built-in; Discord/Twitch would be custom OAuth2 connections (Marketplace pages could not be fetched); Steam has no path (OpenID 2.0).
- Migration from B2C: bulk-import JSON without passwords (email required, custom `user_id`, `app_metadata` for subscription state) then force a password set via reset email/ticket; social users just re-federate. Emit subscription claims from `app_metadata` in a post-login Action (namespaced claim recommended).
- Backend: JWKS at `{domain}/.well-known/jwks.json`; `auth0-api-python`, `express-oauth2-jwt-bearer`; user-event webhooks via Event Streams on every plan; EU tenants in Dublin/Frankfurt.

**Microsoft Entra External ID**
- Cost: $0 up to 50,000 MAU, $0.03/MAU after; SMS-MFA and Go-Local are paid add-ons.
- It does not remove the 24-hour SPA refresh-token cap; the same rule ("24 hours for single-page applications") applies. You get 90 days only by registering the desktop app as a **public client (mobile and desktop)** with `http://localhost` / custom-scheme redirect, doing the flow outside msal-browser (Electron quickstart uses MSAL Node), using password/social sign-in (not email OTP), and checking Conditional Access sign-in frequency. That same fix is available in your current B2C tenant without migrating.
- IdP coverage is narrower than B2C: Google/Apple/Facebook/Microsoft/Entra ID/OIDC/SAML only; no GitHub/Discord/Twitch/X/Steam and no generic OAuth2 connector. Passkeys and email OTP are supported.
- Migration is real work: password hashes can't be exported; official path is Graph bulk import + JIT (`OnPasswordSubmit` extension) or forced resets; the Microsoft tool is a preview/sample. B2C is supported until at least May 2030, so there's no immediate deadline.
- EU data residency at tenant creation (immutable); custom attributes go into tokens via Attributes & Claims; everything scriptable via Graph.

**Unresolved / could not fetch**: Auth0 Marketplace pages for Discord/Twitch (JS-rendered), Auth0 "Powered by Auth0" branding on Free, Auth0 EU-region plan gating, Auth0 refresh-token *maximum*-lifetime default, Auth0 session-lifetime defaults (only in search snippets), Event Streams docs page (404), Auth0 vendor/outage perception (search budget exhausted).
